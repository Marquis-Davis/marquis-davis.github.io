Building an AI Agent for Windows Autopilot Troubleshooting with Microsoft Foundry

September 17, 2026 • 7 min read

Windows Autopilot troubleshooting is usually evidence-heavy. When Enrollment Status Page gets stuck or an application fails during provisioning, the answer is often buried across Intune Management Extension logs, registry state, enrollment information, application IDs, policy data, and device diagnostics.

I have spent years troubleshooting endpoint platforms by collecting that evidence manually, determining which signal matters, and working backward toward the failure. My current AI engineering project asks a different question: what if I could give an AI agent the same evidence an endpoint engineer uses and let it perform the first layer of investigation?

The Idea

I am building a custom troubleshooting agent in Microsoft Foundry around a real Windows Autopilot workflow. The goal is not a generic chatbot. The goal is an agent designed for a specific engineering domain: endpoint provisioning.

The architecture I am working toward looks like this:

Autopilot Device
      ↓
Diagnostic Collection
      ↓ HTTPS
Azure Function / API
      ↓
Azure Storage
      ↓
Microsoft Foundry Agent
      ↓
Evidence Analysis
      ↓
Diagnosis returned to the engineer

The Windows device collects the diagnostic evidence. An authenticated API provides a controlled path into Azure. The evidence is stored for analysis, and the Foundry agent receives instructions and context designed around Autopilot troubleshooting rather than general-purpose conversation.

Why a Customized Agent Matters

An endpoint engineer does not troubleshoot an ESP failure by reading every log from beginning to end. The engineer starts with a hypothesis and moves through useful signals. Is the device enrolled correctly? Did IME start? Which Win32 application is blocking ESP? What state did Intune record? What error was returned? Does the local evidence agree with the cloud state?

That reasoning process is what makes the agent interesting to me.

Instead of asking an engineer to manually correlate every artifact, I want the agent to receive the evidence and return something closer to an engineering assessment:

  • What failed
  • The evidence supporting the diagnosis
  • The most likely failure point
  • What the engineer should inspect next
  • A remediation path when the evidence supports one

Building on Tools I Already Use

This project is not replacing my endpoint engineering background. It is extending it.

I already built a PowerShell troubleshooting tool for Autopilot ESP application failures. It reads ESP-tracked Win32 application state, resolves application names from local Intune Management Extension policy data, and surfaces failed applications with their recorded errors and identifiers.

That local tool becomes even more useful when I stop thinking of its output as something only a human can read. Structured troubleshooting evidence can become input to an AI workflow.

The progression is:

PowerShell troubleshooting
        ↓
Structured endpoint evidence
        ↓
Secure API integration
        ↓
Microsoft Foundry agent
        ↓
AI-assisted engineering decision

The Platform Engineering Part Is Just as Important as the AI

The model is only one component. A useful enterprise solution also needs identity, authentication, authorization, APIs, storage, logging, monitoring, and governance.

That is where this project connects directly to platform engineering. Entra identity can control access. Azure provides the API and storage layer. Microsoft Foundry provides the agent and model orchestration. Endpoint tooling supplies the operational evidence.

The interesting part is connecting those systems securely and making the entire workflow observable.

Where I Want to Take It Next

The first version is intentionally focused on Autopilot. Once the evidence pipeline and agent reasoning are working, the same architecture could expand into Microsoft Graph and Intune so the agent can combine local device diagnostics with authorized cloud-side device, application, policy, and enrollment information.

Longer term, I also want to explore grounding the agent in known troubleshooting documentation and runbooks so it can distinguish between raw evidence, established engineering knowledge, and its own reasoning.

Why I Am Building This

For me, this project represents the bridge between endpoint engineering and AI platform engineering.

I am not learning AI by building a random chatbot. I am taking a problem I understand deeply, Autopilot troubleshooting, and using it to learn agents, APIs, Azure architecture, identity, observability, and Microsoft Foundry.

The endpoint is still where the problem starts. The difference is that the troubleshooting platform now has an intelligence layer.

When PowerShell Downloads Work Manually but Fail in a ConfigMgr Task Sequence

August 2026 • 7 min read

I recently ran into one of those automation problems where everything worked perfectly when I ran it manually, but failed as soon as I tried to make it fully unattended.

The automation was part of a driver packaging workflow I built around Microsoft Configuration Manager.

The workflow was already doing most of what I wanted:

  • Identify when a driver package needs to be updated
  • Locate the correct vendor package
  • Download the package
  • Extract the driver files
  • Create a WIM
  • Copy the WIM to the ConfigMgr content source
  • Create the ConfigMgr driver package
  • Start content distribution

When I ran the PowerShell script manually, the workflow worked.

The problem appeared when I moved the same automation into a ConfigMgr Task Sequence so the entire process could run unattended.

The First Symptom

My logging showed that the script successfully identified the hardware model, located the correct driver package, and validated the version.

Then it reached: 

Downloading driver package...

And stopped.

At first, it looked like the entire Task Sequence had hung.

But the script contained more than one web request, so before changing anything, I wanted to determine exactly which request was causing the problem.

Invoke-WebRequest Was Not Completely Broken

The script used Invoke-WebRequest in two different places.

The first request retrieved a small HTML page that I used to validate information about the driver package: 

$SoftPaqPage = Invoke-WebRequest `
    -Uri $HtmlUrl `
    -UseBasicParsing `
    -ErrorAction Stop

That request worked inside the Task Sequence.

I knew this because the logs continued past that point and successfully displayed the version information.

The second request downloaded the actual executable: 

Invoke-WebRequest `
    -Uri $ExeUrl `
    -OutFile $Destination `
    -TimeoutSec 600 `
    -ErrorAction Stop

That was where the automation stopped progressing.

This was an important distinction.

The problem was not simply: 

Invoke-WebRequest does not work in a ConfigMgr Task Sequence.

The smaller request worked.

The larger file transfer did not.

Why Manual Testing Can Be Misleading

One of the biggest lessons from this problem was that testing a script manually does not always reproduce the environment where the automation will actually run.

When I launched PowerShell myself, I had a normal interactive Windows logon session.

The ConfigMgr Task Sequence was launching the automation through a non-interactive execution context.

Same script.

Same machine.

Same download URL.

Different execution context.

That difference became one of the most important clues in the investigation.

Attempt #2: BITS

My next thought was to use Background Intelligent Transfer Service.

BITS is designed specifically for transferring files and is used throughout Windows, so it seemed like a logical replacement.

I created a small test: 

Import-Module BitsTransfer

Start-BitsTransfer `
    -Source $ExeUrl `
    -Destination $Destination `
    -ErrorAction Stop

I ran the test manually.

It worked.

That looked promising.

I replaced the large Invoke-WebRequest download with Start-BitsTransfer and ran the Task Sequence again.

This time the download did not hang.

It failed immediately.

The Error That Changed the Investigation

My original error handling only told me that the download failed.

That was not enough information.

I changed the catch block so the actual exception would be written to the log: 

catch {
    Write-Log -Message "Download failed: $($_.Exception.Message)"
}

That exposed the real error: 

The operation being requested was not performed because
the user has not logged on to the network.

Exception from HRESULT: 0x800704DD

That changed the direction of the troubleshooting.

BITS was not failing because the URL was wrong.

It was not failing because the destination path was invalid.

The same BITS transfer worked when I ran it interactively.

It failed when the automation ran through the Task Sequence.

The execution context mattered.

Attempt #3: curl.exe

At this point, I wanted the simplest possible HTTPS file transfer.

I did not want to redesign the automation.

I did not want to introduce another service or dependency.

I only needed to replace the part of the workflow that was failing.

Modern versions of Windows include curl.exe, so I decided to test it.

I replaced only the file download with: 

& "$env:SystemRoot\System32\curl.exe" `
    -L `
    --fail `
    --output $Destination `
    $ExeUrl

if ($LASTEXITCODE -ne 0) {
    throw "curl.exe download failed with exit code $LASTEXITCODE"
}

The options are straightforward:

  • -L follows HTTP redirects
  • --fail causes failed HTTP responses to return an error
  • --output specifies the destination file

Since curl is a native executable rather than a PowerShell cmdlet, I also check $LASTEXITCODE.

If curl returns anything other than zero, the script throws an exception and the existing PowerShell error handling takes over.

Then I Ran the Task Sequence Again

The Task Sequence started.

The log reached: 

Downloading driver package...

But this time, it continued.

The next message appeared: 

Extracting Driver Package...

That was the moment I knew the download problem had been solved.

More importantly, I did not have to redesign the rest of the automation.

The existing workflow continued and successfully:

  • Downloaded the vendor package
  • Extracted the driver files
  • Created the driver WIM
  • Copied the WIM to the content source
  • Created the ConfigMgr driver package
  • Moved the package into the appropriate ConfigMgr folder
  • Continued the distribution workflow

The automation was finally able to complete unattended.

Was curl Better Than PowerShell?

Not exactly.

It would be easy to walk away from this and say: 

Always use curl instead of Invoke-WebRequest.

I do not think that is the right lesson.

Invoke-WebRequest, BITS, and curl are all useful tools.

The better question is: 

Which transfer mechanism behaves correctly in the environment
where my automation actually runs?

In this particular workflow:

  • Invoke-WebRequest successfully handled the smaller web request, but the large file download stalled in the Task Sequence
  • Start-BitsTransfer successfully downloaded the file interactively, but failed in the Task Sequence with error 0x800704DD
  • curl.exe successfully completed the same HTTPS file transfer from the Task Sequence

curl was not automatically better.

It was simply the better fit for this execution context.

The Bigger Windows Platform Engineering Lesson

The biggest takeaway from this problem had very little to do with downloading drivers.

It was this: 

Always test automation in the execution context
where it will actually run.

A PowerShell script might eventually execute through:

  • Task Scheduler
  • Microsoft Configuration Manager
  • Microsoft Intune
  • Local System
  • A domain service account
  • A CI/CD runner
  • A remote PowerShell session

Running a script manually proves that the code works under your current interactive session.

It does not necessarily prove that the same script will behave identically when another execution context launches it.

Execution context can affect:

  • Authentication
  • Network access
  • User profiles
  • Environment variables
  • Proxy configuration
  • Certificates
  • Windows services
  • Credential availability
  • Interactive APIs

Understanding where code executes can be just as important as understanding what the code does.

Another Lesson: Improve Logging Before Changing Everything

This troubleshooting process also reinforced how important logging is when building unattended automation.

A log entry like: 

Download failed.

tells me very little.

Capturing the actual exception: 

catch {
    Write-Log -Message "Download failed: $($_.Exception.Message)"
}

can completely change the direction of an investigation.

In this case, the BITS error showed that I was dealing with more than a simple download failure.

Windows was giving me information about the environment in which the operation was being attempted.

For unattended automation, logs are often your debugger.

The Final Download Block

The final implementation remained intentionally simple: 

try {

    Write-Log -Message "Downloading driver package..."

    & "$env:SystemRoot\System32\curl.exe" `
        -L `
        --fail `
        --output $Destination `
        $ExeUrl

    if ($LASTEXITCODE -ne 0) {
        throw "curl.exe download failed with exit code $LASTEXITCODE"
    }
}
catch {

    Write-Log -Message "Download failed: $($_.Exception.Message)"
    throw
}

No redesign of the entire workflow.

No unnecessary complexity.

I replaced the component that was failing and left the rest of the automation intact.

The Simple Version

The troubleshooting path came down to this:

  • The PowerShell automation worked when executed manually
  • The behavior changed when the workflow moved into a ConfigMgr Task Sequence
  • The large Invoke-WebRequest download stopped progressing
  • BITS worked interactively but exposed a non-interactive execution limitation
  • curl.exe successfully completed the transfer from the Task Sequence

The final code change was small.

Understanding why that change worked was much more valuable.

Final Thoughts

This started with a simple question:

Why does my PowerShell download work manually but fail when automated?

The answer turned out to involve more than PowerShell syntax.

It involved execution context.

That is one of the areas I have been focusing on as I continue moving deeper into Windows Platform Engineering: understanding not only how to automate something, but how Windows actually executes, authenticates, and manages that automation behind the scenes.

The experience also changed how I approach similar problems.

Before rewriting working code, I want to know exactly where the failure occurs, what account or context is executing it, and whether the behavior can be reproduced under that same context.

Sometimes the final fix is only a few lines.

Getting to those few lines is where the engineering happens.

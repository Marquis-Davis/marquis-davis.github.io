Invoke-WebRequest Hung, BITS Failed, and curl.exe Finally Worked

August 2026 • 7 min read

I recently hit an issue while trying to make one of my Microsoft Configuration Manager automation workflows completely unattended.

The PowerShell automation itself already worked.

When I logged into the server and ran the script manually, it could download the required package, extract it, build the content, copy it to the ConfigMgr content source, create the ConfigMgr package, and continue the rest of the workflow.

The problem started when I tried to run that same automation non-interactively.

What followed turned into a good Windows Platform Engineering lesson about something that is easy to overlook: 

The same PowerShell code can behave very differently
depending on the execution context.

The Automation

The workflow is part of a larger driver and BIOS automation process.

At a high level, the automation:

  • Checks whether new driver or BIOS content is available
  • Determines which hardware model needs an update
  • Locates the correct vendor download
  • Downloads the package
  • Extracts the content
  • Creates the required WIM
  • Copies the content into the ConfigMgr content source
  • Creates the ConfigMgr package
  • Starts the distribution process

The goal was to remove the last manual step and allow the workflow to run automatically.

That is where things got interesting.

The Script Worked Manually

Before changing any code, I verified the obvious question: 

Does the automation actually work?

Yes.

Running the script manually completed successfully.

That was important because it told me I was not dealing with a fundamentally broken driver automation script.

The problem was related to how the script was being launched.

Moving the Automation into a ConfigMgr Task Sequence

I eventually moved the script into a ConfigMgr Task Sequence and configured the PowerShell step to run under the service account used by the automation.

The Task Sequence started correctly.

The script identified the model.

It located the correct package.

It retrieved the online version information.

Then the log reached: 

Downloading package...

And stayed there.

No error.

No timeout message.

No destination file being created.

The PowerShell process simply remained running.

Finding the Exact Invoke-WebRequest That Was Hanging

My script actually used Invoke-WebRequest more than once.

The first request retrieved a small vendor web page so I could parse and validate information about the package: 

$SoftPaqPage = Invoke-WebRequest `
    -Uri $HtmlUrl `
    -UseBasicParsing `
    -ErrorAction Stop

That request completed successfully inside the Task Sequence.

The logs proved it because the script continued past that point and displayed the expected version information.

The second request downloaded the actual executable: 

Invoke-WebRequest `
    -Uri $ExeUrl `
    -OutFile $Destination `
    -TimeoutSec 600 `
    -ErrorAction Stop

That was the request hanging.

I also checked the destination directory while the Task Sequence was running.

The expected file was not growing slowly.

It had not even been created.

That told me I was not simply dealing with a slow download.

My First Replacement: BITS

The next logical option was BITS.

Background Intelligent Transfer Service is built into Windows and is designed specifically for transferring files.

I created a small one-off test: 

Import-Module BitsTransfer

Start-BitsTransfer `
    -Source $ExeUrl `
    -Destination $Destination `
    -ErrorAction Stop

I ran it manually.

It downloaded the file successfully.

At that point, BITS looked like the fix.

BITS Worked Manually but Failed in the Task Sequence

I replaced the large Invoke-WebRequest download with Start-BitsTransfer.

Then I ran the Task Sequence again.

This time it did not hang.

It failed almost instantly.

The first version of my error handling only reported that the download failed, so I changed it to capture the actual exception: 

catch {
    Write-Log -Message "Download failed: $($_.Exception.Message)"
}

That exposed the real error: 

The operation being requested was not performed because
the user has not logged on to the network.

Exception from HRESULT: 0x800704DD

Now I had something useful.

That Error Was the Clue

The same BITS command had just worked when I ran it interactively.

The URL had not changed.

The destination had not changed.

The server had not changed.

What changed was the execution context.

The Task Sequence was running the automation non-interactively.

BITS was telling me directly that the operation expected a logon/network state that was not available in that context.

That is when I stopped treating this as a normal PowerShell download problem.

I Needed a Downloader Without That Dependency

At this point I did not want to keep redesigning a working automation.

I needed one thing: 

Download this HTTPS file successfully from the Task Sequence.

Nothing more.

Modern versions of Windows include curl.exe, so I decided to try the native executable instead.

The curl.exe Test

I replaced only the executable download with: 

& "$env:SystemRoot\System32\curl.exe" `
    -L `
    --fail `
    --output $Destination `
    $ExeUrl

if ($LASTEXITCODE -ne 0) {
    throw "curl.exe download failed with exit code $LASTEXITCODE"
}

I explicitly used: 

$env:SystemRoot\System32\curl.exe

instead of simply typing curl.

That makes it clear that the automation is calling the native Windows executable.

What the curl Options Do

  • -L tells curl to follow redirects.
  • --fail causes HTTP errors to return a failure instead of treating the response like a successful download.
  • --output writes the downloaded file to the destination path.

Since curl.exe is a native executable, PowerShell does not automatically treat a non-zero exit code like a terminating PowerShell exception.

That is why I also added: 

if ($LASTEXITCODE -ne 0) {
    throw "curl.exe download failed with exit code $LASTEXITCODE"
}

This allows the existing PowerShell try/catch logic to handle a failed curl download normally.

Then I Ran the Task Sequence Again

The script reached: 

Downloading package...

I waited.

Then the next log entry appeared: 

Extracting Driver Package...

That was it.

curl had successfully downloaded the same file that Invoke-WebRequest had stalled on and BITS had refused to transfer.

The Rest of the Automation Continued

This was the part I cared about most.

I did not want a workaround that fixed the download but broke everything after it.

Once curl completed the transfer, the existing automation continued.

It successfully:

  • Extracted the vendor package
  • Processed the driver content
  • Created the WIM
  • Copied the WIM to the ConfigMgr content source
  • Created the ConfigMgr driver package
  • Moved the package into the proper ConfigMgr folder
  • Continued the package distribution workflow

The Task Sequence completed.

The automation that previously required me to log into the server manually could now run unattended.

Three Download Methods, Three Different Results

What made this issue interesting was that all three methods were trying to accomplish the same basic task.

Their behavior was completely different under automation.

Invoke-WebRequest

Invoke-WebRequest `
    -Uri $ExeUrl `
    -OutFile $Destination `
    -ErrorAction Stop

Result: 

Worked manually.
Small web request worked in the Task Sequence.
Large executable download stalled in the Task Sequence.

Start-BitsTransfer

Start-BitsTransfer `
    -Source $ExeUrl `
    -Destination $Destination `
    -ErrorAction Stop

Result: 

Worked manually.
Failed immediately in the Task Sequence.
HRESULT: 0x800704DD.

curl.exe

& "$env:SystemRoot\System32\curl.exe" `
    -L `
    --fail `
    --output $Destination `
    $ExeUrl

Result: 

Worked inside the Task Sequence.
Download completed.
Automation continued successfully.

The Lesson Was Not "curl Is Better"

I do not think the lesson is that everyone should stop using Invoke-WebRequest or BITS.

Both are useful.

I still use Invoke-WebRequest elsewhere in the same automation.

The small HTML request was not the problem, so I left it alone.

There was no reason to rewrite working code.

I changed only the operation that failed in the environment where it needed to run.

The Real Lesson: Execution Context Matters

The most important takeaway for me was: 

Working manually does not prove that an automation
will work non-interactively.

A script may eventually run as:

  • Your interactive administrator account
  • A domain service account
  • Local System
  • A scheduled task
  • A ConfigMgr Task Sequence
  • Intune
  • A CI/CD runner
  • A remote automation service

Those environments are not interchangeable.

Execution context can change:

  • Authentication behavior
  • Network credential availability
  • User profile availability
  • Environment variables
  • Proxy behavior
  • Certificate access
  • Windows service behavior
  • Interactive session dependencies

The PowerShell syntax can be perfectly valid while the environment prevents the operation from behaving the way it did during manual testing.

Another Lesson: Do Not Rewrite Everything Too Early

During troubleshooting, it is tempting to start changing multiple parts of a script.

I deliberately avoided doing that.

The automation had already proven that it could:

  • Find the correct package
  • Parse the vendor information
  • Extract the package
  • Create the ConfigMgr content
  • Interact with ConfigMgr

The failing component was the executable download.

So that is what I changed.

One line of the workflow was replaced instead of redesigning an entire automation system.

Logging Made the Difference

Another takeaway was the value of logging the actual exception.

This: 

Download failed.

tells me almost nothing.

This: 

Download failed: The operation being requested was not performed
because the user has not logged on to the network.
Exception from HRESULT: 0x800704DD

gives me a direction.

When an automation is unattended, the log becomes the closest thing you have to sitting in front of the console watching the problem happen.

The Final Implementation

The final download section ended up being simple: 

try {

    Write-Log -Message "Downloading package..."

    & "$env:SystemRoot\System32\curl.exe" `
        -L `
        --fail `
        --output $Destination `
        $ExeUrl

    if ($LASTEXITCODE -ne 0) {
        throw "curl.exe download failed with exit code $LASTEXITCODE"
    }
}
catch {

    Write-Log -Message "Download failed: $($_.Exception.Message)"
    throw
}

No additional PowerShell module was required.

No separate download service was required.

No redesign of the rest of the automation was required.

The Simple Version

Here is the entire troubleshooting story in a few lines:

  • The automation worked when I ran it manually
  • The large Invoke-WebRequest download stalled when automated
  • BITS worked manually but failed non-interactively with 0x800704DD
  • curl.exe successfully downloaded the same file
  • The existing ConfigMgr automation continued and completed successfully

Final Thoughts

This issue started as a download problem.

It ended up being a lesson about Windows automation.

The final fix was only a few lines of code.

But getting there required proving which operation was actually failing, reproducing the behavior under the real automation context, testing alternatives, and paying attention to what Windows was telling me.

That is one of the things I enjoy about moving deeper into Windows Platform Engineering.

The goal is not just to make a script run.

It is to understand why it behaves the way it does, make the smallest reliable change, and build automation that can operate without someone sitting in front of it.

In this case: 

Invoke-WebRequest hung.
BITS exposed the execution-context problem.
curl.exe finished the job.
